# 文档与资料规则

## 权威位置

一个事实只有一个权威位置。其他文档通过相对链接引用。

| 位置或文档角色 | 保存的内容 | 应放在其他拥有者的内容 |
|---|---|---|
| 根 `AGENTS.md` | 项目常备规则、命令与读取入口 | 长篇教程、模块细节与子目录细则 |
| 子目录 `AGENTS.md` | 子目录专属规则与流程 | 全局或根入口已声明的约束 |
| 根 README | 项目用途、入门路径与导航 | 模块内部细节和完整接口清单 |
| 架构说明 | 系统组成、职责、依赖与扩展方式 | 模块接口细节、执行进度与设计理由 |
| 领域与模块参照 | 所属主题的接口、语义、失败和约束 | 其他领域的实现细节 |
| 模块 README | 使用方式、配置、限制与扩展入口 | 接口注释、生成清单和其他模块说明的复述 |
| 操作指南 | 前提、步骤、结果核对与恢复 | 设计权衡和完整接口参照 |
| 开发指南 | 开发环境、日常流程与验证入口 | 与现有命令配置重复维护的检查清单 |
| 生成参照 | 从源文件生成的类型、配置或接口清单 | 手工修改的派生内容 |
| 事故复盘 | 事件顺序、原因、证据、影响与预防 | 当前接口定义与日常使用说明 |
| 项目 Skill | 可复用工作流与专项判断方法 | 产品契约和已由项目规则定义的条款 |
| `docs/GLOSSARY.md` | 领域术语与定义 | 实现路径、接口清单与执行步骤 |
| `.scratch/issues/<feature-slug>/spec.md` | 本地工作规格、范围与验收 | 已交付行为的长期参照 |
| `.scratch/issues/<feature-slug>/issues/<NN>-<task-slug>.md` | 本地实现步骤、依赖与执行进度 | 长期领域定义 |
| `docs/specs/spec-<feature-slug>.md` | 需随源码交付的长期目标与验收，按需创建 | 日常执行日志 |
| [决策记录](../.agents/notes/AGENTS.md) | 有长期价值的取舍理由 | 其他文档已完整保存的事实，并且无单独记录变更的价值 |
| `.scratch/` | 本地实验、日志、截图与临时材料 | 需随源码交付的权威资料 |

代码与配置是实现事实的来源。参照文档定义当前契约。发现二者不一致时，核对当前指令与验证证据，说明差异后修正拥有者。

用户要求长期保存项目约定时，将内容写入拥有该约定的文件。局部或可逆的约定也可保存到所属文档。

表中的文档角色不要求新建目录或空文件。已有资料沿用实际位置，缺少的资料按任务需要创建。

## 文档层级与范围

文档的主题与所在层级共同限定内容范围。概览只介绍直接下级的用途、职责与主要行为，低层细节链接到所属文档。参照可详述自己的主题，不能因采用参照形式而扩大范围。

测试机制、夹具与工具说明放在最低的实际拥有者处，上层只给入口。生成清单应链接到其来源或生成结果，避免再写一份类型、配置、测试或状态清单。

面向读者的文档应明确采用教程或参照形式。教程提供通向结果的阅读顺序；参照提供可查询的范围与当前语义。两类内容都较长时分开保存，较短的混合章节应标明用途。

教程先确认读者已有知识，再安排概念的前提与难度。只在当前步骤需要时引入新概念；非必需的高级内容放在后续教程或参照中。

架构说明和普通使用资料描述当前状态。长期规格保存已确认的目标与验收。事故复盘、版本化升级材料和历史记录按各自用途保存时间线。

本节的教程与参照结构适用于面向读者的文档。Agent Note 的结构与文字要求由其决策规则管理。

## 资料创建与保留

资料路径相对项目根目录。对应规格与工单使用同一 `feature-slug`，工单序号从 `01` 开始。规格与工单首次有内容时创建，未创建的路径用代码标识说明。

首次确定领域术语时，创建或更新术语表。每个条目使用规范术语、一至两句领域定义与按需填写的避用名称，格式如下：

```markdown
# 领域名称

一至两句领域范围说明。

## 术语

**规范术语**：一至两句定义，说明概念是什么。

避用名称：同一概念曾混用的名称。
```

只收领域概念。实现路径、接口清单、执行步骤与设计理由分别保存在所属文档。避用名称应来自实际混用；没有时省去该行。

多个领域对同名术语有不同定义时，使用各自的术语表，并在项目入口注明对应关系。已有领域术语表与映射时沿用其布局。没有术语时不创建空表。

术语表与长期规格由 Git 跟踪。本地工作规格和工单默认不跟踪。`.scratch/` 文件保存在当前磁盘上，不会因 Git 忽略而自动删除，也不会随新 checkout 出现。

分派任务到其他 worktree、机器或开发者前，确认执行者可读取对应规格和工单。使用共享工单系统、版本控制，或明确复制并核对材料。

长期目标需要随源码交付时，将必要规格保存到上表的长期规格位置。工作材料引用该规格，避免分别维护两份约束。

实现完成后，将当前行为更新到所属契约。普通已关闭工单留在工单系统，或按追溯价值保留、归档或删除，不自动转入 `docs/`。

## 文档写作与维护

创建、重构、评审或审计文档时，执行下方流程。接口说明与注释审查使用本节的语义检查，局部注释要求沿用项目适用的注释规则。

### 文档维护流程

1. **确定用途。** 确认目标资料、读者起点与可观察结果。
   区分教程、操作指南、参照、架构说明和历史记录。
2. **确定拥有者。** 对照所属代码、配置、测试、契约和导航。
   按上方层级规则确定允许展开的范围。
3. **组织阅读路径。** 按教程或参照形式安排内容。
   将下级拥有的细节移回拥有者，保留已知失败及恢复入口。
4. **核对行为声明。** 检查命令、默认值、错误、平台差异与验证证据。
   操作声明依赖执行结果时，记录实际执行的条件与结果。
5. **审查文字。** 使用下方语义保留与独立可读检查。
   当前状态资料分别陈述已有行为与未来目标。
6. **核对派生产物与引用。** 先改源文件，再按项目入口重新生成派生文件。
   移动或删除资料时，在同一变更中修复可编辑入站引用。

教程应写清成功的判断方式及已知失败的恢复方法。参照应覆盖调用者需要的参数、返回差异、失败、时序与副作用。涉及取消、所有权或持久性时，应说明对应行为。

无法执行的操作应报告缺失环境与验证边界。既有事实不能仅因未重跑而删除；先判断它与证据是否一致。未经验证的猜测不能写成已确认行为。

审计或评审只输出发现与处置清单。写作、修复与裁剪请求执行已授权的修改。普通任务覆盖受影响资料及派生产物；全库审计登记整个请求范围。

### 文字覆盖与语义保留

裁剪前，逐句核对原文中有效的主体、动作、条件、时序、所有权与副作用。保留要求强度、禁止条件、例外、失败后果和证据来源。

接口说明应保留正确调用所需的信息。非局部理由和扩展说明链接到所属拥有者。第三方资料按项目维护约定选择范围。

提示词、工具描述、诊断和界面文字可能影响产品行为。先追踪实际使用路径，再按项目要求核对行为证据。文字更短不能单独证明修改正确。

### 独立可读检查

检查读者能否用当前项目资料和可访问的外部出处理解引用、核实事实。用可解析的名称与链接替换会话编号或未保存草稿段落，并保留可证实的事实。

当前状态资料应描述已有行为。评审轮次、个人背书和单次变更叙述不能代替行为依据。待办应指向可追踪的执行材料。

关键词只用于发现候选。用真实问题与近似反例校准搜索，再逐条判断命中；未命中不能证明没有问题。搜索应包含任务范围内的隐藏目录。

保留可解析的工单与标准引用、必要的豁免理由、测量来源和运行时新旧状态。历史记录与事故复盘按其用途保留时间线。版本化升级材料保留受影响行为、升级动作与验收。

例如，“旧连接排空后，新连接才接受请求”描述运行时顺序，应保留。把“未来实现可使用此接口”缩成“实现使用此接口”，会把目标写成已交付事实，应修正这种改写。

Agent Note 的文字与封存引用按[决策记录规则](../.agents/notes/AGENTS.md)维护。

### 验证与交付

改变已记录的公开行为、配置或接口时，在同一变更中更新所属参照与受影响示例。

命令入口或验证条件变化时，在同一变更中更新根 `AGENTS.md` 的命令与测试章节。

Markdown 段落使用一段一行，阅读时使用编辑器软折行。代码块、表格与列表保留各自的结构。

代码块标明实际语言。可执行示例应包含必要前提，并用项目已有工具验证；伪代码或省略实现应明确标注。无法执行时，报告原因与未确认的行为。

引用类型或接口片段时，在同一变更中核对原声明及所属参照。存在生成或一致性检查入口时使用该入口，避免手工维护另一份接口事实。

项目已有多语言文档时，在同一变更中核对受影响版本。沿用现有术语与同步约定，保留未受影响的文字；结构一致不能证明语义一致。

Git 项目在文档变更后运行 `git diff --check`，并检查相对链接。未被 Git 跟踪的新文档应另行检查空白错误。内容涉及可执行契约时，按根 `AGENTS.md` 补充目标行为验证。

重新阅读完整修改段落，核对事实、条件、义务与证据来源。结构检查通过不能替代内容核对。报告检查范围、保留理由、待决项与实际验证。

### 篇幅与重复内容审计

篇幅应服务于读者的任务。检查常用路径长度、一次查询需扫描的无关内容、最大章节与重复事实。字数仅用于定位候选，不作为删除依据。

项目已配置篇幅上限时，超限按以下顺序处理：

1. **迁移内容。** 将其他层级拥有的细节移回拥有者，留下入口。
2. **压缩表达。** 裁剪仍属于本页的重复与叙述，保留完整语义。
3. **修正上限。** 内容确需空间时，说明理由并更新现有配置。

上限是防止资料膨胀的边界，不是删减目标。完整参照可按其查询范围保留必要细节。

审计时逐项核对以下问题：

- 同一规则或理由在多处重复，或在相邻接口旁反复解释。
- 当前状态资料包含变更故事、失效的实现进度或无法解析的会话引用。
- 手工清单与代码、配置或生成来源分别维护，已产生漂移。
- 单段混合多个规则与大量补充说明，读者难以找到适用条件。
- 标题、粗体或强调词过多，掩盖真正改变行为的条款。

发现文字中的承诺不符合任务目标时，先明确行为取舍，再更新拥有者。裁剪说明不能代替授权范围外的产品变更。
