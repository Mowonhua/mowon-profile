# AGENTS.md — 决策记录规则

## 用途

Agent Note 是独立的长期决策记录。它保存已有代码、测试和契约不能解释的理由：为什么选择这个方案，以及放弃了什么。Agent 按本规则选择、创建和读取；文件存在不保证所有讨论决定已保存。

其他资料的归属与写作要求见[文档与资料规则](../../docs/AGENTS.md)。

创建、修改、评审或整理 Agent Note 时，使用[维护工作流](../skills/maintain-agent-notes/SKILL.md)。

## 独立记录的门槛

以下三个条件同时成立时，创建或更新独立记录：

1. 改变决定需要更换依赖、重写多个调用方、变更持久数据或重做已确认的验收。
2. 维护者只看当前代码与契约，会合理质疑这个选择。
3. 决定来自真实方案的权衡，且理由尚未在其他拥有者处完整保存。

一句话足够说明背景、决定与原因时，这三者可只保留一句话；备选方案仍按[正文骨架](#正文骨架)记录。

## 路径与格式

记录存放在 `decisions/YYYY-MM-DD-topic.md`。日期是首次提出的日期。主题应能区分具体决定。文件路径在状态变化时保持固定：状态以 `Status:` 字段为准，原地改写，不移动文件。

### 头部字段

每份记录以标题、`Status:`、`Scope:` 开头。`Scope:` 写受影响的领域、模块或公开契约名称。`Status:` 根据决定的实际状态填写，见[决策状态](#决策状态)。

状态行只写状态词，不带日期和补充说明：文件名记录首次提出日期，其余历史由 git 保存。唯一例外是 `rejected`，写作 `Status: rejected — <一行否决原因>`——查阅被否决记录的读者要找的正是结论。

正文之后是引用字段，使用 Markdown 链接。`Authority:` 链接当前契约，没有对应契约时省去该行。已采纳但未实现的记录使用 `Execution:` 链接执行材料，并说明目标尚未交付；已经落实时省去该行。新记录取代旧记录时加 `Supersedes: [旧记录](相对路径)`，旧记录可编辑时对应加 `Superseded by:`，见[更新与取代](#更新与取代)。

### 正文骨架

正文使用简体中文，以背景开头：动机不依赖方案即可独立成文。内容较少时，背景、决定、原因合并为一段；内容展开时使用规范章节名，真正独特的技术章节（模块拓扑、持久化约定、schema 等）在必需章节之间自由组织。`accepted` 记录的完整结构：

```markdown
# 决策标题

Status: accepted
Scope: 适用领域或模块

## 背景

动机，不依赖方案即可独立成文。

## 决定

现在时态描述已交付的现实：采用什么方案、关键约定是什么。

## 备选方案

**<方案X>**：<一行落选原因>。

## 后果

权衡的代价与收益。

Authority: [当前契约](相对路径)
Execution: [执行材料](相对路径)
```

两种状态的必需章节与时态：

| 章节 | `proposed` | `accepted` |
|---|---|---|
| `## 背景` | 必需 | 必需 |
| `## 提案` / `## 决定` | 必需；可用将来时态描述计划与迁移步骤 | 必需；用现在时态描述已交付的现实 |
| `## 备选方案` | 必需 | 必需 |
| `## 验收标准` + `## 风险` | 必需 | 折入 `## 后果` 或现在时态的 `## 验证` |
| `## 后果` | — | 必需 |

「备选方案」记录讨论中真实出现并被否决的方案，逐一说明落选原因；争议较大的方案可用 `### 为什么不采用 <X>？` 子节。记录决定却不记录它击败的方案，等于邀请反复争论。旧记录的真实备选无法从证据重建时，用以下注释占位，不补造讨论：

```markdown
<!-- 备选方案未记录：证据无法重建 -->
```

`## 验证`、`## 测试`、`## 重新考虑条件` 等章节在陈述现在时态的事实时按需增加。`## 提案`、`## 计划`、`## 验收标准` 是规格用语，不出现在 `accepted` 记录中。

状态转换时同步调整正文：`proposed` 转 `accepted`，将 `## 提案` 改写为现在时态的 `## 决定`，`## 验收标准` 与 `## 风险` 折入 `## 后果` 或 `## 验证`，用实际交付的内容替换计划；`proposed` 转 `rejected` 或 `withdrawn`，正文保留提议时的全部章节（包括 `## 验收标准`），结论只写在状态行。

## 记录文字与证据

记录应在不读取聊天或评审线程时仍可理解。记录之间和记录对外的引用使用相对 Markdown 链接，不使用裸文字或编号：链接可机械检查，文件移动后可机械修复。会话编号、评审轮次和个人背书不能代替决定来源或理由。

同一决定的事实（路径、模块名、键名、默认值）随代码变更在同一变更中同步更新；只更新事实，不改变决定本身。核心选择或理由变化时按[更新与取代](#更新与取代)处理。

裁剪记录时，保留原文中仍有效的适用条件、独有理由、真实备选、后果、验证证据和覆盖缺口。历史事件与否决理由按记录用途保留，删除叙述不能改变选择的含义。

目标与交付的区别按[决策状态](#决策状态)核对。执行清单引用对应执行材料，独立记录只保留解释决定所需的内容。

本节适用于可编辑记录。封存档案按[整理与归档](#整理与归档)维护。

## 决策状态

| Status | 含义 |
|---|---|
| `proposed` | 等待采纳的提议 |
| `accepted` | 已采纳的决定 |
| `rejected` | 在记录的条件下被明确否决 |
| `withdrawn` | 尚未采纳的提议被撤回 |
| `superseded` | 决定已被新决定取代 |

`accepted` 只表示已采纳，不证明决定已实现或验证已通过。记录中的交付声明应指向对应执行证据。

用户明确采纳，或 Agent 在授权任务内选定方案后，才使用 `accepted`。Agent 的待讨论提议使用 `proposed`。未实现的决定应注明目标尚未交付。

状态转换只改写 `Status:` 行，不移动文件，并按[正文骨架](#正文骨架)同步章节名称与时态。

已采纳决定的实质内容被撤销或替换时，另写撤销或替换决定，不把原记录改写成一个不同的决定。

读取 `rejected` 时核对否决条件。否决结论只在这些条件下成立。保留记录时，写清值得重新讨论的条件。

## 更新与取代

先搜索同一主题的拥有者，再决定更新还是新增。同一决定的事实链接可原地修正。核心选择或理由改变时，应创建新记录。

新记录使用 `Supersedes:` 指向旧记录。旧记录可编辑时，使用 `Superseded by:` 指向新记录。新决定被采纳后，可编辑的旧决定才转为 `superseded`。

旧记录已冻结时，新记录单向链接旧记录并说明取代范围。冻结目标保持原文、地址和状态；取代关系以新记录为准。

部分取代时，写清被替代的范围。旧记录保留仍有效的决定，不把整份记录标为失效。可编辑记录通过双方链接说明各自拥有的内容；冻结目标沿用上方的单向链接规则。

被完全取代的记录可按[整理与归档](#整理与归档)合并进当前拥有者并删除原文件。任何合并与删除都不得让 git 历史成为决策依据的唯一副本。

## 读取与维护检查

审查或修改记录前，对照其关联契约和执行证据。设计工作可读取对应 `proposed`。涉及旧备选方案时再读取 `rejected`。已取代和归档记录只用于理解历史。

记录维护完成后核对以下事项：

- 记录已区分用户提议、明确采纳与工程自主选择。
- 章节名称与时态符合记录状态，备选方案已记录真实方案或证据缺失占位。
- 记录中的目标、理由和交付声明与关联证据一致。
- 新旧记录的取代范围和引用关系完整。
- 本次维护涉及的记录事实与可编辑入站链接已修正。

首版通过领域词、相对链接和文本搜索定位。只有定位成本已经影响任务时，才生成只含路径、标题、状态和范围的查询视图。

## 整理与归档

按未来价值逐条判断，避免用字数、年龄或目标数量筛选。先把独有约束、理由、放弃的能力和验证边界迁到拥有者，再合并或删除无独有内容的活跃记录。

仍影响未来变更的理由保持可读。只有尚有历史价值且不再指导当前工作的记录才封存。无历史价值的重复记录在修复引用后移除。否决记录仅在其依据仍能避免一种可能重犯的错误时保留，否则删除。

已被取代或关闭的历史记录可留在原路径。在 `Status:` 下增加 `Archived: YYYY-MM-DD` 后冻结正文；归档不改变决定本身的状态。活跃的 `proposed` 不归档：过时的提议转为 `rejected` 或 `withdrawn`。

封存后保留原文与地址。新的事实写入当前拥有者。旧系统已冻结的档案沿用原冻结规则，不为统一格式而修改。

冻结档案引用活跃文件时，该目标地址应保留。整理目标前检查冻结入站引用；可编辑引用方可改指当前拥有者。

## 验证范围

机械检查可确认记录状态、字段、链接和取代关系的结构。内容核对负责确认决定来源、真实备选方案、记录遗漏、重复和冲突。

普通任务只核对受影响的记录。迁移整个旧决策库时，才逐条登记每份记录的去向和理由。
