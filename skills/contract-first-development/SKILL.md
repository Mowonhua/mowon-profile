# 契约先行开发

## 核心规则

先确定契约，再写行为。契约是 module 的 interface 在代码里的形式：签名和类型写下它们能表达的部分，中文注释写下其余部分。interface 取 `codebase-design` 的定义，指调用方正确使用 module 需要知道的全部事实，类型签名之外还包括不变量、调用顺序、错误模式、必需配置和性能特征。下文的“接口”只指代码里的接口类型或抽象类。

契约是实现的验收面：函数体只需满足契约，测试只通过 interface 观察行为。

## 推进方式

默认在同一轮内从勘察一直做到交付。例外只有两种：

- 用户只要方案、定义或讨论时，交付契约设计，不写函数体。
- 取舍依赖仓库和对话都给不出的信息时，向用户提一个具体问题，例如产品意图、外部调用方的兼容要求、既有持久化数据的迁移方式。

其余取舍按 depth、locality 和仓库既有约定自行决定；选择不显然时，把理由写进相关注释，不写比较过程。

## 步骤

步骤 2 和步骤 3 按 module 循环：确定一个 module 的契约，实现它，再处理下一个。多个 module 的契约相互约束时，例如一方的输出是另一方的输入，先让它们一起完成步骤 2。

### 1. 勘察

读取改动周边的代码，找出可复用的 module、既有契约、匹配的领域类型和文件布局。项目有术语表（如 `docs/GLOSSARY.md`）时，命名沿用其中的规范术语。勘察只为确定归属、避免平行抽象；工具函数是否已存在，在实现时逐个回查。

完成标准：每个预定的契约都在现有结构中找到了归属，或有明确理由新建文件；既有 module 已经承担的职责，通过扩展该 module 实现。

### 2. 确定契约

用 `codebase-design` 的词汇（module、interface、seam、adapter、depth）决定 seam 放在哪里、interface 是什么形状，再把契约写进代码：签名、类型和按“注释格式”书写的中文注释。未安装 `codebase-design` 时，以本步完成标准为准。

- 数据结构优先让非法状态无法表示；类型表达不了的约束写进注释。
- 前端的契约包括组件 Props/Emits、路由与路由参数类型、API 客户端的请求和响应类型。
- 写函数体之前，先按该 interface 在调用方或测试里写出一次调用；调用写得别扭，说明 interface 还要改。
- 实现之前需要编译或运行测试时，函数体和组件模板用最小的合法占位，例如 `throw new Error("Not implemented")`、`todo!()`。
- 被多个 module 依赖的 seam 没有明显最优的 interface 时，可以按 `codebase-design` 的 `DESIGN-IT-TWICE.md` 并行设计几个方案，比较后自行选定。

涉及继承、多态或被多个调用方共享的接口时，再用 `solid` 检查里氏替换、接口隔离和依赖方向。`solid` 的建议与 `codebase-design` 冲突时，以 `codebase-design` 为准：module 的大小由 depth 决定，不套用 `solid` 的行数和实例变量上限；原始类型只在承载领域约束时才包装成值对象。

完成标准：当前要实现的契约已经写进代码，并逐项满足：

- depth：interface 无法再缩小，除非把复杂度推给调用方；设想删掉该 module，复杂度会回到调用方而不是消失，即它不是转发层。
- seam：每个新引入的抽象至少有两个 adapter，测试替身也算；只有一个 adapter 的抽象改为直接依赖具体实现。
- 复用：勘察找到的既有能力没有被重新定义。
- 命名：与代码库和术语表的领域用语一致。

### 3. 实现

一次实现一个可观察行为。关键路径和复杂逻辑先在 seam 上写一条失败的测试，再写刚好让它通过的实现，即 `tdd` 的 red → green；步骤 2 确定的 seam 就是测试 seam，使用 `tdd` 时不再向用户确认。其余行为，以及项目没有测试体系时，用静态检查和实际运行验证。

新建工具函数前，按关键词回查既有工具模块和相邻模块；有相同或相近的函数时直接复用，或者把它提取到共享工具文件、改造成通用函数。

实现暴露出契约缺陷时，先修订契约和对应注释，再继续实现。

完成标准：每个行为都已通过测试或实际运行验证，相关静态检查通过。

### 4. 交付前自检

对本次新增或修改的定义和文件逐项检查：

- 搜索确认步骤 2 引入的占位已全部替换。
- 注释与最终实现一致，实现中改过的契约已同步到注释。
- `实现思路` 只剩代码读不出来的决策和理由，动手前写下的计划已改写为决策或删除。
- 职责字段之外，每条注释字段都承载签名和命名之外的信息。
- 注释不含需求编号、ticket、PR、日期或需求文档名。
- 改动过的文件中，`定义范围` 仍覆盖文件内的全部定义。

完成标准：以上各项全部满足，发现的问题已就地修正。

## 注释格式

注释的读者是之后修改这段代码的维护者，包括 agent。维护者依靠注释确定改动边界，不必重新推导契约，所以注释只写签名、类型和命名表达不了的内容：不变量、调用顺序、错误模式、边界条件、副作用范围、必需配置、性能特征和非显然的设计理由。需求背景和任务情景写进提交信息。

module 的 interface 符号使用下列注释块，包括导出符号、跨 module 调用的函数和类型、持久化或序列化的数据结构。注释块以职责字段开头，写明职责边界；其余字段只在承载签名和命名之外的信息时出现。内部辅助函数只在存在非显然约束时写注释，一行能说清就写一行。

所有语言统一使用下列中文字段名，注释符号按目标语言惯例调整。

文件头：

```ts
/**
 * 文件职责：本文件承载的职责。
 * 定义范围：允许放入本文件的定义类别。
 */
```

数据结构、值对象、DTO、枚举和类型别名：

```ts
/**
 * 结构职责：该结构承载的领域含义。
 * 字段说明：枚举项、联合类型成员或类型别名的含义；有字段的结构改用字段级注释。
 * 约束条件：类型表达不了的取值、缺省或字段组合约束。
 */
```

接口和抽象类：

```ts
/**
 * 接口职责：该接口抽象的能力边界。
 * 调用方：只允许特定 module 调用时写明。
 * 实现要求：实现必须满足的约束。
 */
```

函数和方法：

```ts
/**
 * 函数职责：该函数承担的行为契约。
 * 输入说明：类型之外的参数约束和边界条件。
 * 输出说明：返回值语义、错误、状态变化和副作用范围。
 * 实现思路：代码读不出来的实现决策及其理由。
 */
```

`实现思路` 写为什么这样实现，不写实现了哪些步骤：

- 保留：`实现思路：新连接创建新的加密器，同一连接内清库只替换缓存，避免同一密钥重用 CTR 计数器。`
- 整条删除：`实现思路：拼接实例目录与 backups 子目录。`

确定契约时可以先在 `实现思路` 写下打算采用的做法，实现完成后改写为决策或删除。

字段级注释写在字段旁，说明类型之外的来源、约束和含义：

```ts
interface TaskDraft {
  /** 任务唯一标识，用于在持久化和 UI 状态之间建立稳定引用。 */
  id: TaskId;

  /** 用户输入的原始任务标题，允许为空字符串但不允许为 null。 */
  title: string;
}
```

## 文件布局

新文件以文件头开头。`定义范围` 是归属规则：新增定义放进 `定义范围` 覆盖它的文件；超出所有现有文件的范围时新建文件，或在职责仍然单一时同步扩写 `定义范围`。

文件内包含多类定义时，用区域分隔注释分组，区域依次为：常量、枚举和类型别名；数据结构；接口；函数；导出与注册。语言要求不同顺序时按语言调整。分隔注释只含区域名：

```ts
// ==================== 区域类别 ====================
```
