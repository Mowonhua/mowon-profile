# 功能单元驱动开发（FUDD）

`features/*.md` 是系统功能规格的唯一人工维护来源。每个模块文档把**功能单元**（`F-*`）、**行为场景**（`S-*`）、**功能关系**、**实现符号**和**测试节点**放在同一位置。Agent 与开发者的行为规则写入 `AGENTS.md`。

## 核心概念

- **模块**：按业务或内部职责划分的逻辑分组。一个功能单元只归属一个模块。
- **功能单元 `F-<模块码>-<序号>`**：具有独立目的、稳定职责和长期维护价值的最小系统能力，覆盖用户功能与跨模块内部能力。功能单元是长期资产，**变更集**是单次开发的交付范围。
- **行为场景 `S-<序号>`**：功能单元在指定条件下的预期结果或约束，可先于代码或测试存在。
- **功能关系**：功能单元主动发出的直接关系，只分 `依赖` 与 `触发` 两类。
- **实现符号**：功能单元的主入口和关键实现，格式为 `项目相对路径::定位符`。定位符使用项目可识别的函数、方法、组件、声明或其他稳定名称。
- **测试节点**：验证行为场景的自动化测试，格式为 `项目相对路径::测试定位符`，可使用测试函数、用例全名或框架选择器。测试应断言或观察该场景的预期结果才建立关联。

## 执行步骤

1. **勘察现状。** 如果项目已有 `features/`，读取 `features/README.md` 和目标模块文档。如果项目尚无 `features/` 且任务要求建模，按 [assets/features-README-template.md](assets/features-README-template.md) 和 [assets/feature-module-template.md](assets/feature-module-template.md) 创建最小目录；长期采用本模式时，将 [assets/AGENTS-snippet.md](assets/AGENTS-snippet.md) 并入 `AGENTS.md`。完成标准：已列出受影响的模块、既有 `F-ID` 和 `S-ID`。
2. **逐项判定变更。** 将任务拆成独立需求项，按“功能模型变更判定”逐项归类。拆分、合并功能单元或编写三张表格时，读取 [references/feature-model.md](references/feature-model.md)。新项目建模、多阶段设计或处理缺陷、重构、测试清理与删除功能时，读取 [references/development-workflow.md](references/development-workflow.md)。完成标准：每个需求项都已确定 `F-ID` / `S-ID` 的增改动作，未遗漏既有功能。
3. **更新规格与代码。** 先更新 `features/*.md` 中确认的功能单元和行为场景，再实现代码与测试，最后同步 `功能关系`、`实现` 和 `行为场景` 三张表。实现与已确认规格冲突时，修复实现；仅在需求明确变更时修改规格。如果用户只要求评审或规划，停在规格或计划输出。完成标准：代码、测试与文档中的符号引用完全一致。
4. **校验与验证。** 维护双向追踪或运行 `scripts/featurectl.py` 检查格式、反向索引与变更影响时，读取 [references/traceability.md](references/traceability.md)。按项目语言与框架运行受影响的自动化测试；需要符号级自动校验时，可按追踪规范接入项目检查器。完成标准：`featurectl.py validate` 无错误（可运行 Python 时），未确认的符号已复核或列出缺口，且已记录测试的实际执行结果。
5. **汇报交付。** 输出变更的 `F-ID` / `S-ID`、实现符号、测试执行结论，以及未自动化验证的场景缺口或剩余风险。完成标准：汇报严格区分“文档已关联测试”与“测试已运行通过”。

## 功能模型变更判定

对每个需求项按以下顺序判定：

1. 如果现有规格已覆盖（缺陷修复、纯重构、清理测试），保留原 `F-ID` 和 `S-ID`，只更新代码、测试或引用。
2. 如果需求具备新目的、稳定职责与独立维护价值，新建功能单元 `F-ID`。
3. 如果功能目的不变但支持范围或输入输出扩展，更新功能单元描述，并增改行为场景 `S-ID`。
4. 如果功能职责不变、仅需明确特定条件下的预期结果，只增改行为场景 `S-ID`。
5. 如果既有职责划分失衡，按 [feature-model.md](references/feature-model.md) 拆分或合并，并在旧条目注明 `替代：F-XXX-YYY`。

## 模块文档结构

每个逻辑模块对应 `features/` 下的一个 Markdown 文件。单个功能单元定义格式如下：

```markdown
## F-MOD-001 功能名称

一句话说明功能目标及主要输入、输出或状态变化。

### 功能关系

| 类型 | 功能编号 |
|---|---|
| 依赖 | F-OTH-001, F-OTH-002 |
| 触发 | F-EVT-001, F-EVT-002 |

### 实现

| 角色 | 代码符号 |
|---|---|
| 主入口 | <源文件路径>::<入口定位符> |
| 关键实现 | <源文件路径>::<关键实现定位符> |

### 行为场景

| 编号 | 类型 | 场景与预期 | 测试 |
|---|---|---|---|
| S-01 | 正常 | 满足前置条件时生成结果并更新状态 | <测试文件路径>::<测试定位符> |
| S-02 | 异常 | 输入非法时拒绝执行并保持原状态 | - |
```

表格硬约束：

- `功能关系` 表头固定为 `类型 | 功能编号`。`类型` 只填 `依赖` 或 `触发`，`功能编号` 单元格只填功能的 `F-ID`。
- `实现` 表头固定为 `角色 | 代码符号`。`角色` 填 `主入口` 或 `关键实现`。
- `行为场景` 表头固定为 `编号 | 类型 | 场景与预期 | 测试`。多个测试用逗号 `,` 分隔，暂无自动化测试填 `-`。
- 无对应内容的章节直接省略，不保留空表。
