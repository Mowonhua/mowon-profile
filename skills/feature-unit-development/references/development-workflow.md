# 开发流程与专项任务规范

## 1. 五阶段开发流程

**新项目与架构重整执行完整五阶段；日常变更从阶段 3 开始，按需回溯阶段 1–2。**

### 阶段 1：系统建模

1. 识别领域边界、核心业务对象和逻辑模块职责。
2. 如果项目需要架构说明，创建或增量更新 `docs/architecture.md`。
3. 从现有代码逆向梳理时，区分“已确认的产品需求”与“历史代码的偶然行为”。
   完成标准：每个候选能力都能归入明确的逻辑模块。

### 阶段 2：功能建模

1. 提取面向用户的功能和跨模块稳定内部能力。
2. 对照 `features/*.md` 查重，按 [feature-model.md](feature-model.md) 划分功能单元 `F-ID`。
3. 为每个功能单元编写一句话目的、直接功能关系和关键行为场景 `S-ID`。
   完成标准：`features/*.md` 中的功能定义与场景预期可独立审查，且无跨文件重复定义。

### 阶段 3：变更规划

1. 将当前任务拆解为独立变化项，逐项判定属于新增功能、扩展功能、增改场景或仅实现/测试变更。
2. 结合 `功能关系`、`实现` 表和代码调用链，列出受影响的 `F-ID` 与候选回归测试。
   完成标准：已确定本次变更集涉及的全部 `F-ID` / `S-ID` 及回归测试范围。

### 阶段 4：功能设计

1. 确定接口或入口契约、状态迁移、跨模块协作方式和失败处理策略。
2. 为每个新增或修改的 `S-ID` 指定验证方式（单元测试、集成测试、端到端测试或暂缺）。
   完成标准：所有受影响场景的实现路径与验证方案已确定。

### 阶段 5：实现与验证

1. 按已确认的规格编写代码与测试。测试断言应直接验证 `S-ID` 承诺的预期结果。
2. 使用项目既有工具运行受影响的测试套件、构建与静态检查。
3. 同步更新 `features/*.md` 中的 `功能关系`、`实现` 和 `行为场景` 表格。
4. 运行 `featurectl.py validate` 校验文档结构与引用。仅检查到文件的定位符通过项目工具或人工复核；需自动检查时按 [traceability.md](traceability.md) 接入项目符号检查器。无 Python 运行环境时跳过并向用户说明脚本未运行。
   完成标准：代码、测试、功能文档三者同步，且验证结果已如实记录。

## 2. 专项任务处置规则

**不同任务类型按固定边界维护规格与引用。**

- **缺陷修复（Bug）**：先定位所属 `F-ID` 和 `S-ID`。如果已有场景已声明预期，只修复实现并补充回归测试；如果暴露出未记录的边界或异常规则，补充 `S-ID` 并关联测试。**警告：** 不要把代码的错误行为直接改成规格预期。修改已确认的规格预期应有明确需求依据。
- **纯重构**：保持 `F-ID`、`S-ID` 与场景预期不变。函数或文件重命名、移动、拆分后，同步更新 `实现` 表中的符号路径，并运行关联回归测试。
- **测试清理**：读取 [测试审查规则](test-review.md)，按行为价值决定删改。删除后移除失效引用；有效场景没有其他测试时填 `-`，并说明缺口。仅测试变更不建立审计记录。
- **删除或废弃功能**：删除对应实现与专属测试，清理指向该功能的关系。在原文档保留 `## F-XXX-YYY 名称 已废弃`。有替代功能时注明替代编号。清空该功能的实现、测试和主动关系引用。
- **技术基础设施测试**：格式检查、编译检查、静态分析与探活检查独立于业务功能，不必写入 `features/*.md`。

## 3. 完成标准（DoD）

**交付前逐项核对以下条件：**

- 受影响的功能单元描述、行为场景和模块共用约束已与本次需求一致。
- `功能关系`、`实现`、`行为场景` 三张表的格式合法，无悬空 `F-ID` 或失效符号引用。
- 受影响的自动化测试与静态检查已运行；未运行的检查项已在汇报中注明原因，未标为“已通过”。
- 未绑定自动化测试的场景已填 `-`，并在交付汇报中列出验证缺口。
