# 测试审查规则

## 范围与产出

测试审查回答两个问题：项目应保证哪些行为，现有测试是否有效验证这些行为。

按用户指定的模块或测试范围审查。用户要求全库盘点时，覆盖全部测试入口和测试文件。普通开发只审查本次改动涉及的测试。

审查结论在当次回复中说明，不写审计文件。功能文档只保留当前场景与测试引用。不登记测试编号、测试创建提交或测试处置历史。删除后不保留测试记录。

## 还原行为

1. 读取测试断言、被测实现与真实调用方。
2. 找出触发条件、可观察结果和契约依据。
3. 对照功能文档，关联既有场景。缺少场景时，只补充有明确依据的规则。

行为依据可来自需求、公开 API、模块契约或明确的不变量。历史实现只能作为线索，不能直接升级为有效规格。

例如，测试断言 `Repository.save()` 调用一次，应先确认其目的。若目的只是保证数据持久化，应验证持久化结果。若契约要求避免重复写入，调用次数可能有独立价值。

场景描述写到规则层，不逐个登记测试样例。同一规则的等价输入可属于同一场景；边界与异常仍可能需要独立测试。技术基础设施检查无需强行归入业务功能。

## 判断重复与价值

**同一场景不等于重复测试。** 对候选测试比较以下三项：

- 触发条件与前置状态是否相同；输入是否属于同一等价类。
- 测试是否对同一个可观察结果提出相同要求。
- 是否存在现实缺陷，只让其中一个测试失败。

现实缺陷包括漏分支、条件写反、边界取错、遗漏字段和状态未更新。仅为某个样例刻意编写特判，不算现实缺陷。测试名称相似、调用相同函数或关联相同场景，都不足以判定重复。

按测试组判断边际价值：其他测试保留时，删除当前测试会漏掉什么缺陷？还应考虑测试的稳定性、运行成本和失败定位价值。

| 结论 | 依据 |
|---|---|
| 保留 | 验证必要行为、边界、回归风险，或提供独立的失败定位价值 |
| 合并 | 验证要求相同，合并后保留必要的等价类与边界 |
| 重写 | 行为仍有价值，但断言绑定非契约的实现细节 |
| 删除 | 行为已过时、测试无独立价值，或其他测试已充分替代 |
| 待确认 | 契约依据不明，或需求、实现和测试互相冲突 |

单元测试、mock、私有方法和简单行为本身都不是删除理由。实现细节若属于稳定契约，也可保留测试。

## 精简规则

- **等价类与边界**：保留能区分真实失败方式的输入。参数化用于减少重复代码，不代表减少验证场景。
- **输入可达性**：确认类型系统、上游校验和真实调用方是否已排除该输入。公开 API、SDK 和外部数据入口应按可达输入判断。存在独立防御契约时仍需保留验证。
- **测试层级**：优先选择能观察最终结果且少依赖内部结构的层级。其他层级若验证不同集成边界或提供失败定位价值，可同时保留。
- **测试数量**：按覆盖价值决定数量，不按重要性设置固定上限。
- **辅助证据**：项目已有变异测试或覆盖率工具时，可用其结果复核判断。相同变异结果只说明对已生成变异体的检测能力相同；覆盖率不变不证明行为覆盖完整。

## 执行与验证

1. 列出准备合并、重写或删除的测试及具体理由。
2. 确认删改后如何继续验证有效场景。没有替代测试时，说明缺口。
3. 按用户已授权的范围修改测试。仅分析请求不修改测试；明确授权清理时直接执行。契约取舍不明的项目先保留并提问。
4. 更新功能文档中的当前测试引用。仅测试变更不改场景预期，不分配新功能或场景 ID。
5. 运行受影响的测试和项目要求的检查。跨模块共用夹具或测试入口变化时，扩大验证范围。

完成标准：范围内的测试均已审查，删改有行为依据，当前引用无失效节点，验证结果如实汇报。测试数量下降不是完成标准。
