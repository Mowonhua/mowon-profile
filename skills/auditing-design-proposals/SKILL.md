# 方案文档审查

## 核心原则

执行一次可追溯的设计审计，而不是摘要、润色或泛泛评价。围绕“目标—机制—边界—验证”闭环查找问题；只报告能够用文档证据、跨段冲突或明确缺失项支撑的问题。每个问题必须紧接具体改进建议。

## 输入与输出

- 接收一个方案文档路径；接受用户另行指定报告路径。
- 将输入路径解析为绝对路径。路径不存在、不是文件或无法读取时，停止审查并要求有效路径。
- 未指定报告路径时，写入方案同目录下的 `<方案文件名（不含扩展名）>-审查报告vYYYY_MM_DD_HH_mm.md`。
- 不修改方案原文。若报告路径与方案路径相同，改用上述默认报告路径。
- 使用中文撰写报告；保留方案中的必要英文术语、标识符和接口名。

## 审查步骤

### 1. 建立证据范围

完整读取方案，不以目录、摘要或局部段落代替全文。遵守方案所在仓库的指令文件；仅在方案依赖其他文档、代码或配置才能判断关键结论时读取这些材料，并在报告中列出实际读取范围。仓库存在 `.codegraph/` 且需要定位或理解代码时，先使用 CodeGraph，再使用文本搜索。

完成标准：方案全文已读取；影响关键判断的引用材料已读取，或被明确记录为无法验证的外部依赖。

### 2. 构建“设计承诺表”

在分析过程中提取并对齐以下内容，不必把中间表原样写入报告：

- 目标、非目标、成功指标和验收条件；
- 参与者、组件、职责、权限和唯一权威来源；
- 输入、输出、数据模型、状态、生命周期和版本；
- 主流程、异常流程、时序、触发条件和状态迁移；
- 外部依赖、容量假设、运行环境和硬约束；
- 故障处理、重试、幂等、回滚、恢复和降级；
- 安全、隐私、可观测性、测试、部署、迁移和运维安排。

将同一概念在不同章节中的名称、定义、责任主体、时序和约束相互对照。完成标准：每项核心目标都能追溯到实现机制和验证方式；每条关键数据或状态都能追溯到生产者、消费者、所有者与生命周期，无法追溯之处进入候选问题。

### 3. 按五类问题进行审计

仅保留与当前方案相关的检查项，不为凑数量制造问题。

| 类别 | 重点检查 |
|---|---|
| 逻辑矛盾 | 同一术语定义冲突、目标与机制冲突、前置条件循环、时序不可能、规则互斥、示例与正文不一致 |
| 设计缺漏 | 关键输入输出、异常路径、生命周期、恢复回滚、验收指标、安全权限、观测告警、迁移兼容、测试或运维缺失 |
| 界限模糊 | 组件职责重叠、权威来源不唯一、读写权限不清、事务与并发边界不清、信任边界或适用范围未定义 |
| 可行性风险 | 未验证假设、依赖能力不足、数据或算法不可得、性能容量无依据、资源工期不匹配、部署或外部限制不可控 |
| 完善度问题 | 隐式耦合、不必要复杂度、不可维护或不可演进、配置与版本不可追踪、决策缺少取舍依据、表述无法验收 |

至少沿一条正常链路和两条高影响异常链路逐步推演输入、处理、状态变化、输出与恢复结果。若方案不涉及运行流程，改为推演两个最重要的决策场景和一个边界场景。

完成标准：五类问题均已检查；所有跨章节核心概念均已对照；候选问题已经过证据和影响筛选。

### 4. 验证、合并并排序问题

对每个候选问题执行以下判断：

1. 给出准确位置：优先使用章节路径和行号；无法取得行号时，使用章节名与短摘录。
2. 区分问题性质：
   - `已确认`：文档内部已有直接冲突或缺失足以导致设计无法闭环；
   - `风险`：依赖外部事实或尚未验证的假设，不能表述为既成缺陷；
   - `待确认`：缺少关键决策，必须由方案负责人选择或补充。
3. 评估严重度：
   - `阻断`：核心目标无法实现，或存在不可接受的安全、数据、合规风险；
   - `高`：主流程、职责或关键非功能指标很可能失败；
   - `中`：异常场景、维护演进或交付质量明显受损；
   - `低`：局部清晰度、一致性或工程完善度不足。
4. 合并同一根因产生的重复现象；一个问题只保留一个权威条目，并在证据中列出全部受影响位置。
5. 为问题给出可直接落实的建议：明确修改哪个章节、补充什么规则或机制、由谁负责、何时触发、数据如何流动、状态如何变化，以及用什么验收标准证明问题已解决。存在合理分支时，给出推荐方案及主要取舍。

证据不足时不得猜测。将其降级为“风险”或“待确认”，同时给出验证方法和通过条件。

完成标准：每个问题都有证据、影响、具体建议和验收标准；严重度与证据强度匹配；不存在重复条目。

### 5. 生成 Markdown 审查报告

按以下结构写入目标文件：

```markdown
# <方案名称>审查报告

## 1. 审查结论

- 总体判断：<可实施 / 有条件可实施 / 需重大修改 / 暂不可实施>
- 问题统计：阻断 X，高 X，中 X，低 X
- 首要风险：<一至三条>

## 2. 审查范围与假设

- 方案文件：`<绝对路径>`
- 关联材料：<实际读取的文件；没有则写“无”>
- 未验证依赖：<外部事实或缺失材料；没有则写“无”>

## 3. 优先级总览

| 编号 | 严重度 | 性质 | 类别 | 问题 | 建议动作 |
|---|---|---|---|---|---|
| P-01 | 高 | 已确认 | 界限模糊 | ... | ... |

## 4. 详细问题与改进建议

### P-01 [高][已确认] <可定位根因的标题>

- 类别：<五类之一>
- 位置与证据：<章节、行号或短摘录>
- 问题：<冲突、缺失或风险的准确描述>
- 影响：<失败方式、影响对象和触发条件>
- 改进建议：<可直接写入方案或转化为任务的具体修改>
- 验收标准：<可检查、可测试或可评审的通过条件>

## 5. 待确认决策

| 编号 | 决策问题 | 为什么必须确认 | 推荐选项 | 其他选项与取舍 | 用户决策 |
|---|---|---|---|---|---|

## 6. 建议的修改顺序

1. <先处理会改变总体设计的问题>
2. <再补齐关键闭环和边界>
3. <最后处理完善度问题>
```

没有“待确认决策”时省略第 5 节，并顺延后续章节编号。没有发现某类问题时，不创建空条目，也不输出“未发现问题”或“已检查通过”等说明。不要以“建议进一步完善”“注意性能”等空泛句子充当问题或建议。存在“待确认决策”时“用户决策”列留空，以待用户填写确认最终决策。

### 6. 交付前复核

逐项确认：

- 报告路径符合用户指定值或默认命名规则，且方案原文未被修改；
- 五类问题全部完成检查，正常链路与异常链路完成推演；
- 每个详细问题都能在优先级总览中找到，编号、严重度和性质一致；
- 每个问题下方都有具体改进建议和验收标准；
- 建议之间不存在新的职责冲突、时序冲突或重复权威来源；
- 事实、推断和待确认项已经明确区分；
- Markdown 标题、表格、列表和文件编码有效。

完成标准：目标报告文件存在并可读取，且以上检查全部通过。最终回复只需给出总体判断、问题数量和报告文件链接。
