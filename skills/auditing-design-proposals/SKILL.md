# 方案文档审查

## 审查目标

审查一份方案，产出一份可追溯的设计审计报告。报告只收录能用文档证据、跨章节冲突或明确缺失项证明的问题，不做内容摘要、措辞润色或整体评价。

审查沿**闭环**推进：每个核心目标都落到实现机制，每个机制都有边界，每条边界都有验证方式。目标、机制、边界、验证缺任何一环，都是候选问题。

## 输入与输出

- 方案文档路径由用户提供。用户没给路径时，先询问路径再继续。路径不存在、不是文件或无法读取时，停止审查并请用户提供有效路径。
- 报告默认写入仓库`.scratch/reports/`目录的 `<方案名>-审查报告vYYYY_MM_DD_HH_mm.md`；`<方案名>` 不含扩展名。
- 方案原文只读。
- 报告用中文撰写。方案中的英文术语、标识符和接口名保持原样，用反引号标注。

## 审查步骤

### 1. 建立证据范围

- 完整读取方案全文。
- 只在关键结论依赖其他文档、代码或配置时才读取这些材料。
- 把实际读取范围写进报告第 2 节。

完成标准：方案全文已读取；影响关键判断的材料已读取，或已记录为无法验证的外部依赖。

### 2. 提取设计承诺

审查开始时先提取方案的设计承诺。中间结果不必写进报告，它是第 3 步和第 4 步的输入。

- 目标、非目标、成功指标和验收条件。
- 参与者、组件、职责、权限和唯一权威来源。
- 输入、输出、数据模型、状态、生命周期和版本。
- 主流程、异常流程、时序、触发条件和状态迁移。
- 外部依赖、容量假设、运行环境和硬约束。
- 故障处理、重试、幂等、回滚、恢复和降级。
- 安全、隐私、可观测性、测试、部署、迁移和运维安排。

对照同一概念在各章节中的名称、定义、责任主体、时序和约束，对不上的条目记为候选问题。

完成标准：每项核心目标都能追溯到实现机制和验证方式；每条关键数据或状态都能追溯到生产者、消费者、所有者和生命周期。追溯不到的内容是候选问题。

### 3. 按五类问题审查

只检查当前方案适用的类别。

| 类别 | 检查重点 |
|---|---|
| 逻辑矛盾 | 同一术语定义冲突、目标与机制冲突、前置条件循环、时序不可能、规则互斥、示例与正文不一致 |
| 设计缺漏 | 关键输入输出、异常路径、生命周期、恢复回滚、验收指标、安全权限、观测告警、迁移兼容、测试或运维缺失 |
| 界限模糊 | 组件职责重叠、权威来源不唯一、读写权限不清、事务与并发边界不清、信任边界或适用范围未定义 |
| 可行性风险 | 未验证假设、依赖能力不足、数据或算法不可得、性能容量无依据、资源工期不匹配、部署或外部限制不可控 |
| 完善度问题 | 隐式耦合、不必要复杂度、不可维护或不可演进、配置与版本不可追踪、决策缺少取舍依据、表述无法验收 |

沿一条正常链路和两条高影响异常链路，逐步推演输入、处理、状态变化、输出和恢复结果。方案不涉及运行流程时，改为推演两个最重要的决策场景和一个边界场景。

完成标准：五类问题都已检查；所有跨章节的核心概念都已对照；候选问题都已按证据和影响筛过。

### 4. 定性、定级并合并

对每个候选问题执行以下步骤。

1. **定位**：给出章节路径和行号；取不到行号时，给出章节名和短摘录。
2. **定性**：按「性质」表选一项。
3. **定级**：按「严重度」表选一项。严重度应与证据强度匹配。
4. **合并**：同一根因的重复现象合并为一条，全部受影响位置写进该条的证据。
5. **写建议**：写清改哪一节、补什么规则、由谁负责、何时触发，以及数据和状态如何变化。再写出证明问题已解决的验收标准。存在两条以上可行路线时，给出推荐方案和主要取舍。

证据不足时记为 `风险` 或 `待确认`，并给出验证方法与通过条件。

| 性质 | 判据 |
|---|---|
| `已确认` | 文档内部已有直接冲突，或缺失足以导致设计无法闭环 |
| `风险` | 依赖外部事实或尚未验证的假设，不能表述为既成缺陷 |
| `待确认` | 缺少关键决策，应由方案负责人选择或补充 |

| 严重度 | 判据 |
|---|---|
| `阻断` | 核心目标无法实现，或存在不可接受的安全、数据、合规风险 |
| `高` | 主流程、职责划分或关键非功能指标很可能失败 |
| `中` | 异常场景、维护演进或交付质量受损 |
| `低` | 局部清晰度、一致性或工程完善度不足 |

完成标准：每个问题都有证据、影响、建议和验收标准；严重度与证据强度匹配；同一根因只有一个条目。

### 5. 写审查报告

写入目标文件，结构如下。

- 没有待确认决策时省略第 5 节，后续章节顺延编号。
- 只输出检查出问题的类别。

```markdown
# <方案名称>审查报告

## 1. 审查结论

- 总体判断：<可实施 / 有条件可实施 / 需重大修改 / 暂不可实施>
- 问题统计：阻断 X，高 X，中 X，低 X
- 首要风险：<一至三条>

## 2. 审查范围与假设

- 方案文件：`<绝对路径>`
- 关联材料：<实际读取的文件；没有则写「无」>
- 未验证依赖：<外部事实或缺失材料；没有则写「无」>

## 3. 优先级总览

| 编号 | 严重度 | 性质 | 类别 | 问题 | 建议动作 |
|---|---|---|---|---|---|
| P-01 | 高 | 已确认 | 界限模糊 | ... | ... |

## 4. 详细问题与改进建议

### P-01 [高][已确认] <点明根因的标题>

- 类别：<五类之一>
- 位置与证据：<章节、行号或短摘录>
- 问题：<冲突、缺失或风险的准确描述>
- 影响：<失败方式、影响对象和触发条件>
- 改进建议：<可直接写入方案或转化为任务的修改>
- 验收标准：<可检查、可测试或可评审的通过条件>

## 5. 待确认决策

| 编号 | 决策问题 | 为什么需要确认 | 推荐选项 | 其他选项与取舍 | 用户决策 |
|---|---|---|---|---|---|

## 6. 建议的修改顺序

1. <先处理会改变总体设计的问题>
2. <再补齐关键闭环和边界>
3. <最后处理完善度问题>
```

完成标准：目标文件已写入且可读取，内容符合上述结构。

### 6. 交付前复核

- 总览表与详细问题逐条对应，编号、严重度、性质一致。
- 每条建议与既有职责、时序和权威来源相容。
- 事实、推断和待确认项已分别标注。
- Markdown 标题、表格、列表和文件编码有效。

完成标准：以上各项全部通过。最终回复给出总体判断、问题数量和报告文件链接。
