# 定义先行开发

## 核心规则

分三个阶段开发：先定义，再评审，最后实现。本技能强制让模块边界、数据结构、接口、函数契约和中文注释在行为代码出现之前变得可评审，从而防止过早实现；“定义先行”约束执行顺序，不默认制造跨回合等待。

## 执行模式

先根据用户意图选择阶段 2 的执行模式：

- **默认推进模式**：用户请求实现、构建、重构或完成一项具体工程工作，且没有要求先讨论或先确认时使用。完成阶段 0、阶段 1 和阶段 2 后，输出简短的评审摘要并在同一回合直接进入阶段 3，不提“是否进入阶段 3”。单独使用 `$implement`、`实现`、`按 issue 完成`、`请按上述方案进行优化`、`开始实现` 或 `PLEASE IMPLEMENT THIS PLAN` 等表达属于此模式，不是暂停信号。
- **暂停评审模式**：用户明确要求“先给方案”“只做定义”“等我确认”“逐项讨论”“不要实现”，或阶段 2 发现两个以上会改变公开契约、数据语义、持久化格式或模块边界的可行方案，且现有上下文无法安全选定时使用。阶段 2 检查点结束本回合，等待用户选择或确认。
- **明确一次性信号**：“一次性实现”“无需确认”“直接继续”等表达只取消等待，不跳过阶段 0 至阶段 2；仍须先完成定义和 SOLID 评审。用户明确要求跳过定义评审时，本技能不适用。

如果用户只请求建议、方案或设计讨论，不进入阶段 3；把阶段 2 的结果作为本回合交付物。暂停只用于需要用户作出会改变实现方向的决定，不用于让用户重复确认已经由上下文唯一确定的选择。

## 阶段 0：勘察现有代码

在新增定义之前，先检查现有代码中可复用的模块、既定契约、匹配的领域类型和文件布局，确认新定义的归属。此处只做足以确定边界的轻量发现，不要求预先穷举实现阶段才会暴露的工具函数，也不建立复用清单。

- 优先使用仓库自带的勘察规则。CodeGraph 工具可用时优先使用；只有当图工具不可用或不够用时才退回普通搜索。
- 合适时复用现有契约和领域命名。发现已有模块已经承担相同边界时，调整定义归属，不另起平行抽象。
- 勘察保持轻量：收集到足以避免重复造轮子的证据后，即开始定义工作。

完成标准：预定要写的定义在现有结构中已找到归属，或者有明确理由需要新建文件夹或文件。

## 阶段 1：只写定义

创建或编辑代码文件，使其只包含定义、签名、类型形态、接口契约和详细的中文注释。不实现具体行为。

允许的写法：

- 数据结构、值对象、DTO、枚举、类型别名、接口、抽象契约、函数签名、方法签名、依赖声明和导出。
- 为保持代码可编译而由语言要求的最小占位函数体，例如 `throw new Error("Not implemented")`、`todo!()`、`panic!("not implemented")` 或等价写法。
- 严格遵循下方阶段 1 注释格式的注释。

阶段 1 禁止的写法：

- 真实的分支逻辑、循环、算法、IO、持久化、网络调用、定时器、状态变更、重试、缓存、副作用或领域决策。
- 锁死实现细节的行为测试。静态检查允许且优先。
- 与安放新定义无关的大范围重构。

对于前端场景，额外允许如下写法：

- 组件树与各组件的 Props/Emits 契约（属性与事件）。
- 路由定义与路由参数类型。
- API 客户端函数签名与请求/响应类型。
- 仅包含占位标记和占位内容的可编译组件骨架，以及其必要的 HTML/JSX/template 结构。

前端定义阶段禁止实现具体渲染逻辑、业务逻辑、交互逻辑、事件处理和样式细节。

尽力保持代码可编译。如果语言或框架导致没有具体逻辑就无法编译，加入最小的合法占位，并在检查点中说明该限制。

## 阶段 1 注释格式

所有语言统一使用以下中文字段名。只按目标语言惯用的块注释、文档注释或行注释语法调整注释符号。

文件头注释必须使用此格式：

```ts
/**
 * 文件职责：描述本文件负责承载的定义范围。
 * 定义范围：列出允许放入本文件的类型、接口、函数契约类别。
 */
```

区域分隔注释必须使用此格式，不加任何额外标签前缀：

```ts
// ==================== 区域类别 ====================
```

数据结构、值对象、DTO、枚举和类型别名必须使用此格式：

```ts
/**
 * 结构职责：说明该数据结构承载的领域含义。
 * 字段说明：说明关键字段、枚举项或类型别名的数据来源、约束和含义。
 * 约束条件：说明字段为空、缺省、非法值或组合约束。
 */
```

接口和抽象契约必须使用此格式：

```ts
/**
 * 接口职责：说明该接口抽象的能力边界。
 * 调用方：说明预期由哪些模块或对象依赖该接口。
 * 实现要求：说明实现该接口时必须满足的约束。
 */
```

函数和方法必须使用此格式：

```ts
/**
 * 函数职责：说明该函数或方法要完成的行为契约。
 * 输入说明：说明参数来源、关键约束和边界条件。
 * 输出说明：说明返回值、错误、状态结果或副作用边界。
 * 实现思路：自然语言描述的实现思路，不写可执行逻辑，只专注于怎么做，而不关注什么时候做。
 */
```

数据结构、DTO、配置对象和事件对象中的关键字段必须有字段级中文注释：

```ts
interface TaskDraft {
  /** 任务唯一标识，用于在持久化和 UI 状态之间建立稳定引用。 */
  id: TaskId;

  /** 用户输入的原始任务标题，允许为空字符串但不允许为 null。 */
  title: string;
}
```

如果字段含义已由命名完整表达，且结构注释已说明整体语义，可以省略字段级注释。不要写只复述字段名的空注释。

禁止把实现计划写进注释。实现意图只写在函数注释的`实现思路`字段中，函数体保持最小的合法占位语句。

禁止在注释中遗留任务情景表述：不得引用 ticket 号、需求编号、PR 号、日期、需求文档名或任何临时上下文。注释只描述代码自身的稳定契约，需求背景归提交信息或任务系统。

## 文件与区域布局

每个新文件都以上述文件头注释格式开头。文件内只允许包含与其职责和定义范围相关的定义。

使用以下默认区域顺序，只有当语言要求不同的合法顺序时才调整：

1. 文件职责注释
2. 导入与依赖
3. 常量、枚举和类型别名
4. 数据结构、值对象和 DTO
5. 接口和抽象契约
6. 函数和方法定义
7. 导出、注册和适配器声明

区域之间用上述分隔格式加简明的中文区域名分隔。同类函数放在同一区域。如果一个文件开始混入不相关的职责，先拆分再继续添加定义。

## 阶段 2：用 SOLID 评审

**必选子技能：**本阶段必须使用 `solid`。`solid` 无法加载时，按下方检查项逐条自行评审，不得因此跳过评审。

在进入阶段 3 之前，评审每一条新增或修改的定义。检查项：

- 文件、模块、类型、接口和函数的单一职责。
- 接口隔离：不让调用方被迫依赖用不到的方法。
- 依赖方向：高层策略依赖抽象，不依赖具体基础设施。
- 开闭设计：只在当前需求需要的地方保留扩展点。
- 继承或多态契约的里氏替换安全性。
- 对照阶段 0 勘察到的仓库现有能力，检查重复造轮子风险。
- 命名与代码库领域语言的一致性。
- 注释准确性：注释遵循阶段 1 格式，描述定义本身和预期实现，不写空泛的填充内容。
- 注释情景干净：注释中不含 ticket 号、需求编号、PR 号、日期或需求文档名等任务情景表述。

评审中发现的问题立即修复，然后重新运行相关静态校验。

完成标准：定义集已经用 `solid` 评审过，重复能力风险已处理，静态校验已运行或已明确无法运行的原因。

## 阶段 2 检查点

阶段 2 检查点是质量门，不自动等同于用户确认：

- 默认推进模式：记录 SOLID / 重复能力的评审发现、修复结果和静态校验命令，然后直接进入阶段 3。检查摘要可以出现在过程更新或最终交付中，不提出等待确认的问题。
- 暂停评审模式：本回合停止，不实现具体逻辑。检查点回复只能包含：
  1. SOLID / 重复能力的评审发现与修复。
  2. 已运行的静态校验命令，包括失败或跳过的检查项。
  3. 一个直接、具体的确认或选择问题。

除非用户要求，不要附上文件清单、文件职责摘要、定义清单或未实现函数清单。

## 阶段 3：通过检查点后实现

默认推进模式在阶段 2 检查点通过后直接开始；暂停评审模式只有在用户确认或完成选择后才开始具体实现。

开始实现时：

- 行为变更采用测试先行开发。有 TDD 技能或项目测试约定时，遵循它。
- 用满足已确认设计的最小行为切片，把占位函数体替换为真实逻辑。
- 实现中每要新建一个工具函数，先进行一次针对性的关键词回查，检查既有工具模块与相邻模块；已存在相同或相近函数时，直接复用，或将其提取到共享工具文件并改造成通用工具函数，不在本模块内另建重复实现。
- 随实现变化同步更新中文注释，使其描述真实的运行逻辑、数据流、状态变化和边界处理。
- 实现过程中持续保持 SOLID 约束；如果实现压力暴露出定义缺陷，停下来修订定义，而不是绕过它打补丁。

完成标准：具体逻辑已实现，注释与实现一致；涉及前端时，渲染、样式和交互也已完成；相关测试或校验命令已通过或已被如实报告。

完成后按用户当前请求交付结果。只有用户明确要求提交，或仓库/任务流程明确把提交列为交付物时才创建提交；提交时只纳入本次任务确认范围内的文件，并遵循仓库提交规范。

## 常见错误

| 错误 | 纠正 |
| --- | --- |
| 阶段 1 就写进部分真实逻辑 | 改回占位函数体，把预期实现写进中文注释。 |
| 没查现有代码就新建接口 | 先做轻量勘察，复用匹配的契约。 |
| 把注释当成事后补的文档 | 定义阶段就写注释，并随每次代码改动同步更新。 |
| 默认推进模式误当成暂停 | 已完成定义与 SOLID 评审且没有未决契约，却在阶段 2 结束回复并等待用户；记录非阻塞检查摘要，直接进入阶段 3。 |
| 暂停评审模式未等待 | 用户明确要求先确认，或存在无法安全推断的契约取舍，却直接实现；输出阻塞检查点，等待一次具体确认或选择。 |
| 把“一次性实现”理解为跳过定义 | 为了减少等待而跳过阶段 0 至阶段 2；只取消等待，仍先完成勘察、定义和 SOLID 评审。 |
| 把所有定义堆进一个文件 | 按文件职责拆分，并保持区域顺序稳定。 |
| 实现工具函数前不回查，多个模块各自重复实现同一功能 | 新建工具函数前先按关键词回查既有工具，命中相同或相近函数时复用或提取到共享文件通用化。 |
| 注释残留“Ticket03 要求……”这类任务情景表述 | 删除临时上下文，把注释改写为描述代码自身稳定契约的内容。 |
