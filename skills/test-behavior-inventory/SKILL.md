# 测试行为盘点与清理

对项目的测试代码做一次行为盘点：建立两份长期维护的测试治理清单，给出每个测试的处置建议，经用户确认后执行实际的测试清理。

## 核心规则

- 一行行为记录代表一个“被测试固化的行为”，优先关注用户可观察行为、模块契约和业务不变量。
- 产出两份表，共同构成项目的长期测试索引：
  - `BEHAVIORS.md` 记录项目需要长期保证、且有明确依据的行为契约，描述“项目应该保证什么”。
  - `TEST-DISPOSITION.md` 记录现有测试与行为契约之间的对应关系、维护状态和处置结论，描述“目前通过哪些测试保证这些行为，以及这些测试应如何维护”。
- 两份表帮助后续开发快速回答：某个行为是否已有测试覆盖？某个已有测试在保护什么行为？修改某个行为时需要同步检查哪些测试？新增测试是否与已有测试重复？
- 后续任何新增、修改、删除测试的工作，都应同步维护这两份表，使其始终与当前行为契约和测试代码一致。
- 被删除或废弃的条目只更新状态，必须保留 ID、最终状态和处置原因；禁止复用已废弃的行为或测试 ID。
- 两份表默认建在项目根目录；用户指定了位置时按指定。项目已有两份表时增量更新，沿用既有 ID 体系；新增行为先与既有行为按三项判定查重，命中则让测试指向既有行为 ID。
- 两份文档的标题、用途说明与表结构以本技能 `assets/` 下的模板为准，填充数据行时不添加其他表格或示例行；可视化视图会解析文档内的全部表格，额外表格和示例行会被当成真实数据。

## 阶段一：建立行为清单

1. 扫描项目结构，找出所有测试代码及测试入口。仓库存在 `.codegraph/` 索引时优先使用 CodeGraph 定位和理解测试代码，否则使用文本搜索。
2. 逐个分析测试实际固化的行为，首次建立时把本技能 `assets/BEHAVIORS.template.md` 复制为项目根目录的 `BEHAVIORS.md`，逐行填充：

| ID | 模块 | 行为 | 层级 | 依据 | 重要性 | 稳定性 | 状态 |
| ---- | ---- | ---- | ---- | ---- | ------ | ------ | ---- |

字段定义：

- `ID`：唯一行为编号，例如 `B-001`；废弃后不再复用。
- `模块`：行为所属模块、组件或领域。
- `行为`：用自然语言描述测试真正保证的行为，描述“系统应该怎样”。
- `层级`：`L1` 用户/外部可观察行为；`L2` 模块或组件契约；`L3` 实现细节。
- `依据`：该行为为何应存在。优先使用产品需求、API/模块契约、领域规则、明确的不变量、项目文档、代码中明确表达的设计约束；只能从历史实现推断时，明确标记为“历史实现”。
- `重要性`：`关键`、`高`、`中` 或 `低`。
- `稳定性`：`稳定` 应长期保持；`可变` 合理但实现或设计可能变化；`偶然` 主要由当前实现造成，没有明确契约依据。
- `状态`：`有效` 当前仍然成立；`过时` 已经过时；`存疑` 无法确定。

3. 行为还原：把“调用某个函数”“调用某个 mock”“调用次数必须为 1”“某个私有方法被调用”“某个内部数据结构恰好如此”“某个当前实现步骤发生了”等断言，先还原为它所服务的上层行为再记录。例如 `test_create_user_calls_repository_save_once` 应分析其是否真正表达“创建有效用户后，用户数据必须被持久化”：调用次数是当前实现细节，持久化才是需要保证的行为，两者区分开。还原时保留触发条件、输入域和断言结果的差异，这些差异是三项判定的依据。
4. 过度测试识别：重点寻找这些模式——大量 mock 内部实现而不是验证结果；对调用次数、调用顺序做没有明确契约依据的严格断言；测试私有方法或内部辅助函数；同一行为在多个测试层级重复验证且低层测试没有额外价值；为覆盖代码行而产生没有行为价值的测试；大量绑定当前实现结构，导致正常重构就要修改大量测试；验证已不存在或已改变的历史行为；测试的异常本身并非项目需要保证的契约；大量测试相同输入、只改变没有实际意义的实现细节。
5. 重复行为识别：主动寻找“不同测试实际上测试同一件事”。判定前先过三项判定，三项同时满足才算同一行为，任何一项不满足就视为不同行为：
   - 触发条件与前置状态相同：同样的输入域、同样的前置数据；
   - 断言的可观察结果相同：对同一结果提出同一要求，而不是相关要求；
   - 失败集相同：举不出只让其中一个失败、另一个仍然通过的合理实现缺陷。
   同一模块、同一函数、相似命名、同一主题只是候选线索；成功路径、参数校验、唯一性约束、权限边界、并发、异常恢复是不同契约。
   多个测试通过三项判定固化为同一行为的，只建一条行为记录，阶段二让这些测试指向同一个行为 ID。
6. 对全部行为完成分层和有效性判断，任何测试文件都不得遗漏。

完成标准：所有测试文件中固化的行为都已登记入表；每个行为都具备层级、依据、重要性、稳定性和状态；判定为同一行为的测试只对应一条行为记录。

## 阶段二：测试处置

1. 建立测试与行为之间的映射，首次建立时把本技能 `assets/TEST-DISPOSITION.template.md` 复制为项目根目录的 `TEST-DISPOSITION.md`，逐行填充：

| ID | 测试 | 文件 | 行为 ID | 测试类型 | 处置 | 原因 | 替代测试 | 创建提交 | 状态 |
| ---- | ---- | ---- | ------- | -------- | ---- | ---- | -------- | -------- | ---- |

字段定义：

- `ID`：唯一测试编号，例如 `T-001`。
- `测试`：测试名称。
- `文件`：测试所在文件相对项目根目录的路径。
- `行为 ID`：该测试实际固化的行为，可填写多个 ID。
- `测试类型`：`行为`、`契约`、`集成`、`单元`、`实现`、`回归` 或 `其他`。
- `处置`：`保留`、`合并`、`重写`、`删除` 或 `待确认`。
- `原因`：说明具体原因，不能只写“冗余”或“过度测试”。
- `替代测试`：删除或合并时填写能够继续覆盖该行为的测试；没有则填写 `—`。
- `创建提交`：首次引入该测试的提交，写 7 位短 hash，定位规则见「提交关联」。
- `状态`：`生效中` 当前仍然存在且有效；`已删除` 已被删除、不再存在于代码中，通常因为冗余、过度测试、过时或没有实际价值；`已取代` 不再是当前主要测试、职责已被另一个测试取代，通常意味着发生了测试重构、合并或测试层级调整。

2. 按以下规则对每个测试给出处置建议。处置以测试保护的行为价值为依据，与测试当前是否通过无关：

**保留**：满足以下之一——固化重要的 L1 行为；固化明确且稳定的 L2 契约；防止高风险回归；对关键边界条件有明确价值；虽然是实现层测试，但该实现本身就是明确且需要长期保证的契约。

**合并**：多个测试通过三项判定固化同一行为时合并，优先保留更接近真实行为、更稳定、更少绑定实现细节、能覆盖更多重要场景的测试。

**重写**：测试表达的行为仍有价值，但测试方式过度绑定当前实现时重写。例如当前验证 Service 内部调用 `Validator.validate()` 一次，应改为验证非法输入最终被拒绝。

**删除**：满足以下之一——行为已经明确过时；只验证没有独立价值的实现细节；与其他测试完全重复且没有额外覆盖价值；验证的行为不是项目应承诺的契约；重复验证更高层测试已充分覆盖的内容，且没有独立的失败定位价值。

**待确认**：以下情况不自行删除，标记待确认并向用户说明——无法判断行为是否仍是产品或业务要求；看似历史遗留，但仍可能代表重要兼容性要求；文档、代码和测试之间存在冲突；无法确定是否为故意设计；删除后可能影响外部 API、兼容性或数据格式。

3. 处置自查：检查是否存在遗漏的测试和相互矛盾的处置。逐条复核指向同一行为 ID 的测试组：组内测试的断言结果存在差异，或能举出只让其中一个失败、另一个仍然通过的合理缺陷时，把行为拆回独立记录再分别处置——把不同行为并成一条记录，会让有独立价值的测试被合并或删除，代价高于保留少量冗余。重复判定存疑时按待确认处置，交付时列为待用户决策的分歧。处置的目标是用尽可能少、尽可能稳定、尽可能有意义的测试，覆盖项目真正需要长期保证的行为，而不是减少测试数量：有价值的边界测试不删；测试是单元类型、使用 mock、行为看起来简单，都不构成删除理由；测试难写或代码改动频繁，也不构成删除仍然重要行为的理由；判断行为是否过时要结合实现、文档、调用方和项目结构，不能只看测试代码本身。

完成标准：每个测试都有唯一的处置结论和具体原因；所有删除与合并都注明替代测试或覆盖缺口；待确认项已单独汇总。

## 提交关联

`TEST-DISPOSITION.md` 的 `创建提交` 列记录每个测试的首次引入来源；行为表不登记提交，需要追溯某个行为的落地提交时，查看固化它的测试的创建提交即可。治理视图在测试展开详情中展示提交，并通过本地 git 自动读取提交时间与提交信息悬浮显示：

- 创建提交优先用本技能 `scripts/sync-commits.py [项目根目录]` 自动登记：脚本按测试名与文件路径用 git 定位首次引入提交，原位回填表中为 `—` 的单元格（已登记的行不动），并在报告中列出未登记的行与原因；建立两份表和阶段三更新表格后各运行一次。`--check` 不改文件，校验已登记的 hash 指向真实提交、且测试名确实出现在该提交的文件内容中，报告的告警需人工复核。
- 脚本未能定位的测试，再按规则手工定位：提交整体新增测试文件时用 `git log --diff-filter=A --format=%h --follow -- <文件>`；测试后加进既有文件时用 `git log --reverse -S '<测试名>' --format=%h -- <文件>`，均取最早一条。
- 单元格只写 7 位短 hash；仓库没有版本历史、测试尚未提交或定位不到时填 `—`，不臆测。提交时间与提交信息原文不写入文档，视图按 hash 从当前仓库实时读取，始终与提交本身一致。
- 提交信息的自动读取依赖随视图提供的本地服务器（`TEST-GOVERNANCE.bat` 或 `scripts/view.py` 启动）；改用普通静态服务器时视图只能显示 hash，不影响两份表的维护。

## 可视化视图

首次建立两份表时，把本技能 `assets/TEST-GOVERNANCE.html` 同名复制到项目根目录（项目已有则复用）；Windows 主机同时复制 `assets/TEST-GOVERNANCE.bat` 与 `assets/TEST-GOVERNANCE-server.py`，日常查看双击该文件即可自动启动本地服务器并打开浏览器。视图从同目录的 `BEHAVIORS.md` 与 `TEST-DISPOSITION.md` 实时读取，之后维护两份表无需改动这两个文件。视图还会尝试读取同目录的 `TEST-RUN.xml`（JUnit XML 格式的最近一次测试运行报告）。运行测试时按框架把报告写到该文件：pytest 加 `--junitxml=TEST-RUN.xml`，vitest 加 `--reporter=junit --outputFile=TEST-RUN.xml`，jest 使用 jest-junit reporter，go 使用 gotestsum 的 `--junitfile TEST-RUN.xml`。`TEST-RUN.xml` 是运行产物，首次建立两份表时把它加入项目 `.gitignore`。非 Windows 主机或需要自定义端口时，运行本技能 `scripts/view.py`（用法 `python view.py [项目根目录] [端口]`，自动打开浏览器，另支持 `--no-open` 与 `--exit-busy` 参数）或任选静态服务器后访问 `/TEST-GOVERNANCE.html`；提交信息按 hash 的自动读取由 `view.py` / `TEST-GOVERNANCE-server.py` 提供接口，改用普通静态服务器时视图中只显示 hash。

## 交付与确认

确认分析完整后，向用户交付两份表与视图访问地址，然后结束回合等待确认：列出待确认项与需要用户决策的分歧，说明确认后将执行的删改。用户确认之前不修改任何测试代码。

## 阶段三：执行清理

用户确认后，按最终处置结论修改代码。

修改完成后：

1. 运行本次改动涉及的测试，再运行完整测试套件，确认没有产生新的测试失败。运行测试时输出 JUnit XML 报告到项目根目录的 `TEST-RUN.xml`（pytest 加 `--junitxml=TEST-RUN.xml`，其他框架的输出方式见可视化视图一节），供治理视图展示最近一次运行结果。
2. 更新两份表，使其反映最终代码状态；被删除的测试和废弃的行为只更新状态，保留 ID 与处置原因。

完成标准：测试套件通过且无新增失败；每个 `有效` 行为都有对应的保留测试；两份表与最终代码状态一致。
